Can System-One AI Models Classify Electrocardiogram Exam Images?

ECG
AI
Experiments
What happened when I asked two typed AI decision models to read 827 ECG images, and how I checked their discrimination and calibration.
Author

Felipe Meneguitti Dias

Published

October 15, 2026

I was curious about a simple question: what happens if we give an ordinary 12-lead ECG image to an AI model built to make structured decisions? Can it recognize common ECG findings without being trained specifically as an ECG classifier?

There are plenty of models trained on ECG signals. But here I wanted to test something different: two general-purpose, image-capable decision APIs, asked to look at the exam just as a person would see it on a page.

This is an exploratory experiment, not a clinical diagnostic tool. I have linked the images, prompts, predictions and analysis code so the results can be checked.

Two models that return decisions

The phrase System-One AI refers here to systems designed for relatively direct, structured decisions. It should not be taken as a literal claim about human psychological System 1.

I compared Jev 1.14.0 from TypeSafe AI and GPT-6 Luna Decisions, accessed through OpenAI’s Decisions API. Both accept an image and answer typed questions with choices such as YES or NO. Importantly for this experiment, both also return scores for the possible answers.

That is useful for evaluation. A YES/NO prediction tells us what the model decided. Its score also lets us ask whether positive ECGs tend to receive higher probabilities, and whether those probabilities correspond to what actually happens.

The CODE Test experiment

I used 827 ECGs from the CODE Test set, with reference annotations for six findings. These are recordings that have been rendered as images of 12-lead ECG exams. Neither model received the original digital waveform, a clinical history or the reference labels.

RBBB Right bundle branch block 34

This is a multilabel problem. An ECG can contain more than one finding. Six negative answers mean only that none of these six labels was identified, not that the ECG is necessarily normal.

From ECG signals to images

The exams were rendered with ecg-plot, using the Sangha-style layout also used in my doctoral research. The plotting library takes the recorded signals and draws a familiar ECG page, with the leads arranged as a printed exam.

The images and their reference labels are available in the CODE Test image repository. You can open an example ECG there.

For a fair API comparison, I resized each image once, preserving its aspect ratio, and sent the same PNG to both models. Downscaling may hide small ECG details, so this choice is also a limitation worth remembering.

What exactly did I ask?

I deliberately kept the instructions short. I wanted a zero-shot baseline, rather than explaining ECG interpretation rules to the models.

For Jev, each of the six questions followed this template:

Assess the 12-lead ECG image in `ecg_image`.
Is {condition} present?
Evaluate this finding independently of other diagnoses.

YES: {condition} is present
NO:  {condition} is absent

For example, for atrial fibrillation:

Is Atrial fibrillation present?
Evaluate this finding independently of other diagnoses.

GPT Decisions received the equivalent question and the same image. The request format differs between the APIs, but the diagnostic task is the same. Neither model saw the ground truth.

The complete request code is available for Jev and GPT Decisions.

An example of the answers

For the LBBB question on ecg_0, both models answered NO, correctly. But the scores were quite different.

Jev:

{
  "choice": "NO",
  "probabilities": {"YES": 0.49, "NO": 0.51}
}

GPT-6 Luna Decisions, converted to the same format:

{
  "choice": "NO",
  "probabilities": {"YES": 0.00, "NO": 1.00}
}

This is why I wanted to look beyond classification accuracy. Two models can make the same decision while expressing very different levels of certainty. These are probabilities reported by the decision APIs, not automatically validated clinical risks.

How I evaluated the models

Jev returned results for all 827 exams. GPT Decisions returned valid results for 826, with one failed inference (ecg_818). For the statistical comparison, I excluded that exam from both models, leaving 826 matched ECGs.

I examined two related but distinct properties.

Discrimination asks whether the model gives higher positive scores to ECGs that really contain a finding. I measured this with the area under the receiver operating characteristic curve, or AUROC. A value of 0.5 is roughly chance-level ranking, while 1.0 is perfect separation.

Calibration asks whether a reported probability agrees with the observed frequency. If a model assigns a 70% probability to many exams, we would expect roughly 70% of those exams to be positive in a well-calibrated group. A model can discriminate well and still be badly calibrated.

I used the Brier Score as a complementary measure of probability quality:

\mathrm{Brier}=\frac{1}{N}\sum_{i=1}^{N}(p_i-y_i)^2

Here, p is the probability of YES and y is the reference label, either 0 or 1. Lower Brier scores are better. Brier is not a pure calibration measure, since it also reflects discrimination and the prevalence of the condition.

The macro-AUROC was 0.692 for Jev and 0.778 for GPT Decisions. GPT Decisions had better AUROC in five of the six classes. The exception was LBBB, where Jev reached 0.976, compared with 0.953 for GPT Decisions.

GPT Decisions also achieved a lower mean Brier Score across the six findings, 0.033 versus 0.169 for Jev. That suggests better probability predictions on this dataset, although a proper calibration assessment also needs to consider the low prevalence of most labels.

The confidence intervals in the figure quantify sampling uncertainty for each model. They are not a formal test of the difference between models. With only 13 positive AF cases and 16 positive SB cases, the calibration curves in particular should be read cautiously.

What comes next?

The CODE Test was a useful first experiment, but 827 exams are not enough for a broad assessment of ECG interpretation, especially when some conditions have very few positive cases.

Two natural next steps are:

  • PTB-XL, a much larger public collection with 21,799 ECG recordings and multiple diagnostic labels. We can evaluate image renderings across a broader set of findings and examine performance across more patients.
  • George B. Moody PhysioNet Challenge 2024, which focuses specifically on ECG images, including scans, photographs and simulated paper artifacts. It is a good way to test how robust the models are when an exam is no longer a clean digital rendering.

Those datasets are proposed follow-up evaluations, not part of the results shown above. Their label definitions and image formats differ from CODE Test, so they will need their own carefully specified protocols.

Final thoughts

Both APIs could read an ECG image and return structured diagnostic decisions. That is interesting, but it is not the same as reliably interpreting an ECG.

In this small test, GPT Decisions generally discriminated better and produced better probability scores. Jev performed particularly well at ranking LBBB cases. The differences between diagnoses were substantial.

For me, the main lesson is that getting a YES/NO answer, ranking cases correctly, and reporting trustworthy probabilities are three separate achievements. All three deserve to be measured before considering a model for clinical use.

The inference code, Python figure generator and original CODE Test images are available for reproducibility. No results in this article should be used for patient care.
